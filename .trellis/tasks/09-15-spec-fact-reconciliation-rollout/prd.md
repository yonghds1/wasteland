# spec 事实对账（全量推广）

## Goal

按风险分批核验 `.trellis/spec/**` 中**关于本仓库客观状态**的断言，把与代码不符的改对。

### 为什么做

`CLAUDE.md` 要求 AI 不凭预训练记忆猜架构，并把 `.trellis/spec/` 定为 Single Source of Truth
——所以 spec 的每条事实断言都是后续每个会话的**决策输入**。试点（`09-15-spec-fact-reconciliation-pilot`）
实测 `quality-guidelines.md` 的 **31 条事实断言中 14 条已过期（45%）**，并挖出一处"假承诺"：
spec 声称存在三类注册守卫，实际 `CommandManager.register()` 零校验、重复名静默覆盖。

谎报"**做了**"比谎报"没做"更危险——贡献者会据此依赖一个不存在的保证。

## Method（试点产出，推广必须遵循）

**判据 R1**：该句是否在断言"本仓库当前的客观状态"？
- 是 → 纳入核验；
- 否，属行为规范 → 不纳入、不改；
- 边界情形（规范的**前提事实**已被推翻）→ 只改前提，不动规范本身。

**试点补充规则 R1b（必要）**：改前提时**必须显式区分"要求如此"与"当前就是如此"**。
试点 D-2 节（注册守卫）既有规范又内嵌事实断言，若不显式标注，读者仍会把要求误读为既成事实。
写法参考：`**Duplicate guard** *(required · NOT implemented)*: …`。

**R2 不许抽查**：逐条进对账表，每行含
`断言原文（含行号）→ 判定（属实 / 已过期 / 属规范不适用）→ 核验证据（命令或文件）→ 处理`。
**"仍然属实"同样必须给证据**——否则等于没查。

**R3 整段陈述必须拆条**：`Observed Baseline` / `Current Check Commands` / `Gaps` 这类整段描述
是漂移高发区（试点中它们贡献了绝大多数过期项），不允许"这节看起来还行"就跳过。

**R4 只改事实描述**：不动规范措辞、不统一文风、不为显新而加时间戳。

**R5 每文件产出对账表**（`research/reconciliation.md`），可由第三方独立复核。

**R6 每批次必扫四个维度**（第 2 条为 runtime-contracts 批次暴露后补，此前缺失）：
1. `src/**` 路径存在性；
2. **旧品牌名**——`.rxc`、`RXC_`、`rx-cli`、`joe`、`JOE_`。只扫 `src/` 路径会**整块漏掉**配置与
   env 文案（runtime-contracts 批次中最大一处漂移就是这样漏掉的，共 18 行）；
3. 代码块标识符对码（函数 / 类型 / 类）；
4. **区分代码块与 `Wrong` 反例块**——反例里的标识符是刻意伪代码，按"过期"去修会破坏示错意图。

**R7 "找不到"必须归因**：判定"某文件/符号不存在"前，先确认**自己的匹配手段是否够全**。
实例：`ChatInputBar.test.ts` 被两轮判为"不存在"，真因是匹配模式不含 `.tsx`。

**R8 "找得到"不等于"写得对"**（R7 的镜像，runtime-contracts 收工自审暴露）：
验证签名时，**确认符号存在只是第一步，必须接着核对完整签名**。
实例：我把 `loadRxcSettings` 改名后，只验了新名存在，**没看签名**——而同一块里的
`resolveChatRuntime` 缺 `cwd?` / `agentMode?`、`runAgentLoop` 缺 18 个可选参数与返回类型的一个字段。
做法：签名类断言一律**读源码定义处**（`grep -A N "export function X"`），不要停在 `grep -l`。

## Rollout Order（按风险，不按字母）

试点经验：**成本差异主要来自文件类型**，而非行数——"文件/脚本存在性"类断言便宜且命中率高；
"签名/契约"类需逐条对码，**实测成本约为存在性型的 2–3 倍**（109 个标识符逐个 grep）。

| 批次 | 文件 | 类型 | 状态 |
|---|---|---|---|
| ✅ 0 | `backend/quality-guidelines.md` | 存在性型 | 已完成（31 条断言 / 14 条过期，约 45%） |
| ✅ 1 | `backend/runtime-contracts.md` | 契约型 | 已完成（约 40 条可机械核验断言 / 6 类过期，42 增 29 删） |
| 2 | `backend/tool-runtime-contracts.md` | 契约型 | 747 行，按契约型系数（2–3×）估工 |
| 3 | `backend/logging-guidelines.md` | 存在性型为主 | 633 行；Gaps 节刚被试点证伪过一条 |
| 4+ | `backend/` 其余 → `frontend/` → `guides/` | — | 待前几批校准后重排 |

顺序理由：`CLAUDE.md` 明确把 AI 指向 backend 的架构与记忆设计，故 backend 优先；
契约型文件引用密度高、过期后果最重（读者会照签名写代码），故排在存在性型之前处理。

## Acceptance Criteria

- [ ] AC1：各批次的子任务全部完成并归档，每个文件都有落盘的对账表。
- [ ] AC2：**.trellis/spec 中不再有"与代码相反的事实断言"**——最终以一次全量复扫为准：
      对每个文件重跑该文件的核验命令，过期项为零。
- [ ] AC3：所有"改了前提"的条目均按 R1b 显式标注了"要求 vs 现状"。
- [ ] AC4：跨批次汇总统计（各文件断言数 / 过期率 / 实测成本），用于判断剩余批次是否值得做。
- [ ] AC5：`npm run check` 与 CI 全程绿（纯 markdown 改动，但实证而非假设）。

## Out of Scope

- `docs/` 目录的修正——各子任务只**记录**由此暴露的 docs 漂移，汇总后另行决定。
- 规范性条文的增删改（R4）。
- 记忆文件（memory）维护。
- 新增规范：本任务只让 spec 与现实的描述一致，不规定现实应当如何。
- 防复发机制的设计（根因疑似是这类"已观察状态"段落只写一次、之后无人回看；
  本任务不承诺给出方案，但 AC4 的统计应能为将来讨论提供依据）。
